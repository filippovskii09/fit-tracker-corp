# PR Description

Create a PR or MR description from the current git state.

## Rules

1. Never mention AI tooling, assistants, or autogenerated authorship in the title, body, or git history summary.
2. Do not create or modify a PR automatically unless the user explicitly asks.
3. Prefer `full branch` scope against the detected base branch unless the user asks for another scope.
4. Write the description for a reviewer first.
   The summary should explain user impact and product behavior before file-level implementation details.

## Workflow

1. Identify branch context.
   Detect the current branch and detect the most likely base branch from git history.

2. Select review scope.
   Use one of:
   - staged changes
   - last commit
   - commit range
   - full branch vs base

3. Analyze the diff.
   Collect:
   - changed files
   - high-level user-facing impact
   - whether the change is a fix, feature, refactor, chore, perf, docs, or test
   - any config or dependency implications

4. Build the description.
   Use this structure unless the user asks for another one:

   ```md
   ## Description

   <2-4 sentences for a non-technical reviewer>

   ## Related Issue

   - <issue link or ticket link>

   ## Screenshot/Video

   <!-- Add screenshots or video demonstrating the change -->

   ## Configuration

   <Only include if the change adds or changes config>

   ## Related PRs / Dependencies

   <Only include if relevant>

   ## Testing

   1. <manual scenario>
   2. <manual scenario>
   3. <manual scenario>
   ```

5. Output:
   - Title
   - Body
   - Base branch
   - Optional notes about anything suspicious in scope

## Title Format

Use:

`type: short human description`

Where `type` is one of:
- `feat`
- `fix`
- `refactor`
- `chore`
- `docs`
- `perf`
- `test`

Keep the title under 70 characters.
