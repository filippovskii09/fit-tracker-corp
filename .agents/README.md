# AI-Assisted Development Workflow

`.agents` is the canonical project-owned source of truth for AI-assisted work in this repository. Root-level and tool-specific files such as `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, and `.gemini/styleguide.md` are thin adapters that point agents back here instead of copying the full rules.

## Repository Context

Fit Tracker Corp is a TypeScript monorepo:

- `backend/`: NestJS API with TypeORM, PostgreSQL, DTO validation, auth, workouts, exercises, users, and Jest tests.
- `frontend/`: React, Vite, React Query, MUI, Tailwind, i18n dictionaries, service clients, route guards, and Jest/RTL tests.
- `docs/`: project documentation and learning notes.
- `.agents/rules/`: stable repository rules.
- `.agents/skills/`: reusable workflows for specific task types.

## Start Here

Every agent should begin with this sequence:

1. Read this file.
2. Read `.agents/skills/common-agent-rules/SKILL.md`.
3. For implementation tasks, inspect the affected code before proposing or editing.
4. Load only the task-specific skill or rule files needed for the current task.
5. Treat `.agents` as canonical when tool adapters disagree with deeper project rules.

| Task | Use |

## Roles

Agents may split work internally, but the final responsibility stays with the main agent.

- Main agent: owns user intent, git safety, final scope, implementation quality, validation, and reporting.
- Investigator or explorer: maps the codebase, identifies sources of truth, compares options, and reports facts without editing.
- Builder: makes a small, scoped implementation after the source of truth is clear.
- Reviewer: inspects the diff for bugs, regressions, missing validation, duplicated rules, and over-broad changes.

## Workflow

### Investigation

Use investigation when the request is ambiguous, architectural, cross-cutting, security-sensitive, or asks for options.

1. Define the question and affected domain.
2. Search existing code, docs, tests, services, routes, DTOs, query keys, and config before proposing new structure.
3. Identify the source of truth.
4. Explain current behavior, constraints, options, risks, and a recommended path.
5. Include a validation plan and source links when external docs influenced the recommendation.

### Implementation

1. Confirm the current git branch and working tree.
2. Read the relevant rules and task skill.
3. Inspect existing patterns before editing.
4. Keep the change minimal and focused.
5. Avoid duplicate abstractions, duplicate constants, parallel service clients, or alternative rulebooks.
6. Add or update tests when behavior changes.
7. Run the most relevant validation available locally.
8. Report changed files, validation results, residual risks, and any rule deviations.

### Review

Review like a maintainer, not like a formatter.

1. Lead with correctness, security, data loss, auth, persistence, API contracts, cache invalidation, and test gaps.
2. Cite exact files and lines where possible.
3. Flag broad refactors, generated-looking code, duplicated logic, hidden behavior changes, and missing edge cases.
4. Keep summary secondary to findings.

### Issue Creation

Use issues to capture reproducible, bounded work.

Include:

- problem statement and user impact;
- current behavior and expected behavior;
- affected area and source of truth;
- acceptance criteria;
- implementation notes when useful, without over-prescribing internals;
- validation plan;
- risk notes for auth, security, env, database, migrations, or data changes.

### PR Description

Use `.agents/skills/pr-description/SKILL.md`. PR descriptions should be reviewer-focused and should not mention AI tooling or autogenerated authorship.

## Safety Rules

- Do not run destructive git commands or modify remote state unless the user explicitly asks.
- Do not push branches unless explicitly requested.
- Do not overwrite user changes.
- Do not broaden scope into unrelated refactors.
- Treat auth, security, environment variables, database schema, migrations, encryption, cookies, and token flows as high-risk.
- For high-risk work, require stronger validation and call out residual risk clearly.
- Prefer existing project vocabulary, constants, services, DTOs, routes, query keys, and test utilities.
- Never create a second source of truth for rules that already live in `.agents`.

## Quality Bar

AI-assisted work is acceptable only when it improves speed without lowering review quality.

Block or revise output that:

- invents APIs, files, requirements, or configuration;
- ignores existing project patterns;
- changes behavior without tests or an explicit reason;
- duplicates rules across adapters;
- hides uncertainty;
- skips relevant validation;
- makes broad cosmetic changes unrelated to the task.
